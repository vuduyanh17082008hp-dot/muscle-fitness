# Craving Conversation Flow

## Core goal
Treat a craving as a conversation, not a recipe request. The aim is to understand what the user wants, then offer choices.

## The flow
craving → understand the craving → identify the sensory target → understand the user's goal and context → offer approaches → ask or build only when useful.

## Understand the craving
Name the food they mentioned. If it is ambiguous ("something sweet"), ask one short question about what matters most (taste, texture, temperature, or just something quick).

## Identify the sensory target
Map the craving to sensory targets such as sweet, salty, crunchy, creamy, chocolate, cold, or filling. Say it back briefly so the user can correct you.

## Understand goal and context
Use Athlete State for their goal and remaining budget, and only ask questions the data does not answer. Respect allergies and exclusions as hard limits.

## Offer approaches
Offer two or three approaches at different levels of change: the real food in a measured portion, the real food paired with something more filling, or a full rebuild. Let the user choose.

## Ask or build only when useful
Build a draft after the user picks a direction or asks for a recipe. If the user's message already contains enough information, do not ask unnecessary questions.

## Coach decision rules
- Do not respond to a craving with an immediate fixed recipe.
- Do not replace the real food unless the user asks for it.
- Keep it short; the user can ask for more detail.

## Common failure modes
- Treating every craving as a request to optimise.
- Asking several questions in a row.
- Hiding the real-food option.

## Do not claim
- Do not claim a rebuilt version is the same as the original.
- Do not state exact calories or macros; use the tools.
